# Progress — 2026-09-25 17:06 UTC — fix: Firebase CDN cached the transcript 404

Second fix for "transcript never appears". `2026-09-25-1648-transcript-404-stuck.md`
found a real bug (the transcript query stopped polling) and fixed it — **but that
was not the whole story.** This note corrects the conclusion and fixes the actual
blocker.

## What the previous note got wrong

It concluded the UI simply "stopped asking". True at the time, but the user's own
network dump afterwards showed the *fixed* UI polling `/transcript` dozens of
times and still getting `404 "Transcript not ready"` forever. So there were two
bugs stacked; only the first was fixed.

## The real blocker: the CDN was answering, not the API

Evidence, in order:

1. The browser fires `GET /api/projects/{id}/transcript` repeatedly (dozens of
   requests in the user's curl dump).
2. Cloud Logging had **exactly one** `/transcript` entry for that project — the
   first one. The rest never reached Cloud Run.
3. `TranscriptService.get` called directly against live Firestore returns all 68
   segments. The data was never missing.
4. Same request straight to the Cloud Run URL: **200** with the full transcript.
5. Same request through `habeas-codus.web.app`: response headers show
   `x-served-by: cache-bom-…` — Firebase Hosting's CDN is in the path.
6. The decisive one: a **404** came back with `cache-control: max-age=600`, while
   a **200** came back with `cache-control: private`.

So Firebase Hosting cached the 404 at its edge for ten minutes. The first poll
lands ~37 s before the worker writes the transcript, gets a 404, and every poll
after that is answered by the CDN with the stale error while Cloud Run is never
called. The project flips to `ready` (that query isn't a 404, so it isn't cached),
the processing card disappears, and the transcript never shows up — exactly the
reported symptom.

## Root cause

`firebase.json` rewrote `/api/**` to Cloud Run with **no `headers` block**, and
the API set no `Cache-Control` of its own. Firebase Hosting then applies its own
default caching to rewrite responses. Every authenticated, per-user API response
in this app is wrong to cache at any layer.

## Fix — both layers

1. **Origin (`backend/app/main.py`)** — the request-id middleware now also sets
   `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache`, and
   `Vary: Authorization` on every response. This covers AppError, HTTPException
   and validation-error responses, which all pass back through that middleware.
2. **Edge (`firebase.json`)** — new `headers` block for `source: /api/**` with the
   same values, so the CDN is told not to cache even if the origin forgets.

The origin fix is the one that matters; the hosting config is belt and braces.

## Regression tests

`backend/tests/test_cache_headers.py` covers the four response paths:
success, the exact `404 "Transcript not ready"` case, 422 validation, and 401
from the auth dependency. Each asserts `no-store` + `Vary: Authorization`.

## Gotcha worth keeping

**Firebase Hosting caches rewrite responses by default.** A 404 from a
`/api/**` rewrite gets `max-age=600` unless the origin says otherwise. This is
invisible in local dev (no CDN) and only shows up as "the data exists in the
database but the UI says it doesn't". When debugging a UI that disagrees with
Firestore, check `curl -D -` response headers for `x-served-by: cache-*` before
suspecting the backend.
